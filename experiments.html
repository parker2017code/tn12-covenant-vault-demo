Kaspa TN12 covenant proof lab. Testnet only.

Rules attached to testnet money.

This page tracks experiments where spendable outputs carry rules. Some paths landed on TN12. Some bad paths were rejected locally. Replay artifacts explain accepted state.

Read this first Not mainnet DeFi. Not audited custody.

The goal is to show which rule moved the money, which rule blocked the wrong move, and what a wallet could show before signing.

Evidence classes

Do not read every row as the same kind of proof.

Accepted TN12 evidence, local rejects, and replay-derived state are useful for different reasons. The page keeps them separate.

Accepted TN12

A transaction or payload event landed on testnet and is linked through a txid, response, fixture, or artifact.

Local reject

A candidate failed in the local script or covenant engine. Useful for testing, but not a broadcast rejection.

Replay-derived

The repo reads accepted rows and calculates app state. Replay explains state; it does not by itself control funds.

What changes

The spend carries more of the rule.

A normal app can track a budget, payout, asset, or game step in a private database. These examples ask whether the spend itself can carry the rule, then let the app replay accepted records into readable state.

Bitcoin-like

Money lives in UTXOs: spendable chunks with clear ownership.

Programmable

Rules can affect how value moves, but state travels through outputs instead of one global contract account.

Kaspa

Fast ordering makes multi-transaction UTXO workflows easier to inspect as workflows, not only isolated settlement records.

Functional examples

Read each proof as a product job.

The artifacts matter because they show what moved, what was refused, and what a wallet or app could explain before the user signs.

Budget Allowance or team budget

Money can move under a visible limit, then the remaining money is locked back into the next budget state.

  • User job: parent wallet, team treasury, grant stream, merchant payout limit, game resource.
  • Crypto point: the bad spend is refused by the spend path where the script enforces it, not only by a dashboard.
  • Technical name: recurring-cap covenant. Accepted on TN12; user-wallet signing and audit still separate.
Step Turn or staged workflow

One step goes to one role, returns with valid state, or recovers through timeout if it stalls.

  • User job: game turn, dispute step, service job, staged approval, claim/challenge flow.
  • Crypto point: the accepted path becomes public evidence that a private server cannot silently rewrite.
  • Technical name: mux / worker contract family. Proves routing and timeout mechanics, not full game rules.
Asset Controlled asset move

An asset moves only when the required controller input appears in the same transaction.

  • User job: ticket, access pass, game item, license, settlement right, app-owned asset.
  • Crypto point: ownership follows transaction rules instead of a platform account row.
  • Technical name: sibling-input authorization / ICC. Accepted strike on TN12; negative rows are local rejects.
Reject Vault safety review

Negative checks show the obvious bad moves: wrong signer, wrong destination, missing relock, over cap, and stale reset.

  • User job: explain why a vault, escrow, or family wallet does not drain on a bad click.
  • Crypto point: refusal evidence is stronger than a happy-path demo.
  • Boundary: local script-engine rejects unless an artifact says TN12 accepted/rejected.
Group Release or refund

Coordination evidence shows fresh pledge outputs taking release paths and a separate fresh set taking refund paths.

  • User job: group buy, event deposit, public-goods grant, club project, cooperative funding.
  • Crypto point: release/refund can be inspected from public evidence instead of only trusting a campaign database.
  • Boundary: threshold selection is still transparent replay/planner logic.
Pay Conditional payout

Scheduler receipts tie an intent, bids, execution receipt, and a guarded payout spend into one reviewable story.

  • User job: subscription, payroll window, recurring payout, tournament turn, stale-action guard.
  • Crypto point: users can replay whether the action was eligible before trusting the payout story.
  • Technical name: scheduler receipt plus covenant payout. Payout spend is accepted; trigger eligibility is still replay-derived.
